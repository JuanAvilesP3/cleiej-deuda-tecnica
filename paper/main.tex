\begin{abstract}
\noindent Software produced in university courses and capstone projects is widely assumed to carry more technical debt than comparable open-source work, but this has rarely been tested for Latin America. We compare 274 academic GitHub repositories (identified by thesis and course keywords, with contributors located in Latin America) against 275 non-academic repositories matched by language and size on nine static metrics, using Mann-Whitney U tests with Holm correction and Cliff's delta. Contrary to our hypothesis, academic code shows \emph{significantly lower} cyclomatic complexity (median 2.16 vs.\ 3.12, $\delta=-0.37$, $p<10^{-11}$). Inheritance depth is higher in academic Java code ($\delta=+0.29$, $p=0.003$); coupling, cohesion, duplication, and test-file presence do not differ significantly. A check using stars as a maturity signal does not support attributing this to the small, unlabeled control repositories. SonarQube on a 415-repository subset corroborates the complexity result ($\delta=-0.458$, $p<10^{-14}$) and finds a slightly lower technical debt ratio in academic code ($\delta=-0.142$, $p=0.025$). Self-admitted technical debt markers run in the hypothesized direction: 42.2\% of academic repositories contain at least one, against 23.0\% of controls ($\delta=+0.190$, $p<0.001$).
\end{abstract}

\keywords{Technical debt, software engineering education, empirical software engineering, Latin American software, code complexity, GitHub mining.}

\section{Introduction}

It is commonly assumed, among educators and practitioners alike, that code written for a course assignment or a thesis project carries more technical debt, in the sense of the metaphor introduced by Cunningham~\citep{cunningham1992wycash} (higher complexity, near-zero test coverage, more duplicated code), than comparable work produced outside an academic setting. This assumption motivates a large share of software-engineering curriculum design, yet it is rarely tested with a matched, quantitative comparison, and to our knowledge no such comparison has been run specifically for Latin American academic software, where institutional resourcing, course structure, and open-source contribution culture may all differ from the North American and European settings most existing studies draw on.

This paper runs that comparison directly. We ask whether repositories produced in Latin American university courses and capstone/thesis projects differ measurably, on a set of standard static metrics, from a size- and language-matched sample of non-academic repositories, and if so, in which direction and by how much. We report the result even where it contradicts our starting hypothesis, because a null or reversed finding here is itself informative about what ``academic code'' means empirically in this region, as opposed to what it is assumed to mean.

The contributions of this work are: (1) a size- and language-matched quantitative comparison of Latin American academic software against non-academic controls, at a scale (549 repositories) sufficient for non-parametric hypothesis testing; (2) a report of an inverted finding, lower and not higher complexity in academic code, with the alternative explanations we could test (language, repository age, size, control-group maturity) and their results; (3) a cross-tool consistency check of the central finding with SonarQube Community, which agrees on the complexity result and isolates a tool- and sample-dependent difference in duplication rate.

\section{Related Work}

An early in-depth exploration of technical debt by Tom, Aurum, and Vidgen~\citep{tom2013exploration} combined a review of the literature with practitioner interviews to describe the dimensions of technical debt (among them code, design and architecture, testing, and documentation debt), why it arises, and its consequences; this vocabulary frames the kinds of debt our metrics and SATD markers can and cannot capture. Li, Avgeriou, and Liang~\citep{li2015mapping} subsequently mapped 94 studies on technical debt and its management, classified TD into ten types, and found that code-related debt has received the most attention, while calling for more empirical studies with high-quality evidence. We are not aware of a prior study that compares academic and non-academic code on these metrics, controlled by language and size, at the scale reported here.

Santos et al.~\citep{santos2017external} conduct a systematic literature review of external quality metrics for object-oriented software; we apply metrics of the coupling, cohesion, and complexity families they review to a labelled academic/non-academic comparison. More directly relevant, Hamer et al.~\citep{hamer2021using} use Git-derived metrics to measure students' and teams' code-contribution patterns within university software-development courses, across eight projects with 150 students, showing that repository-level metrics can characterize academic software engineering practice; our study extends this direction from process metrics (who contributed what) to product metrics (what the resulting code looks like structurally), and from within-course comparisons to a labeled comparison against non-academic repositories. Mateos et al.~\citep{mateos2017managing} apply the same Chidamber and Kemerer~\citep{chidamber1994metrics} object-oriented metric suite this paper uses, in their case to relate service-interface complexity to the underlying object-oriented implementation; their use of CK metrics as an early, development-time complexity signal is consistent with how this paper treats complexity metrics generally, as a proxy available before a system reaches production, not as an after-the-fact quality judgment. The repository-mining methodology follows the practices established by Kalliamvakou et al.~\citep{kalliamvakou2014promises} and refined by Munaiah et al.~\citep{munaiah2017curating}, both of which show that many GitHub repositories are personal, inactive, or not engineered software, so samples need filtering before structural metrics can be read as representative of software engineering practice; our fork exclusion and 10-commit minimum follow that advice in a simplified form. Munaiah et al. explicitly list homework assignments as an example of the non-engineered repositories that such filtering removes, which is a reminder that our academic sample is, by design, drawn from the kind of repository that engineered-project studies exclude.



The self-admitted technical debt analysis in Section~3.4 is grounded in a body of work that began with Potdar and Shihab~\citep{potdar2014satd}, who identified SATD in the source-code comments of four large open-source projects (Eclipse, Chromium OS, Apache HTTP Server, and ArgoUML), found it in 2.4\% to 31\% of files, and reported that more experienced developers introduce most of it, while time pressure and code complexity do not correlate with how much SATD is present; their figures are per file, so they are not directly comparable with our repository-level rates (42.2\% academic vs.\ 23.0\% control). Bavota and Russo~\citep{bavota2016satd} extend this line of work to a large-scale study of how SATD spreads and evolves across many open-source projects. Maldonado and Shihab~\citep{maldonado2015satd} read more than 33,000 comments and classify SATD into five types (design, defect, documentation, requirement, and test debt), with design debt the most common; our marker list (\texttt{TODO}, \texttt{FIXME}, \texttt{HACK}, \texttt{XXX}, \texttt{BUG}) is a simpler keyword approximation of the comments they analyse manually. Huang et al.~\citep{huang2018satd} subsequently detect SATD in source comments automatically with a text-mining approach that combines feature selection with a composite classifier trained on several projects; we use the simpler keyword approach because precision is less critical for our research question (is the \emph{prevalence} of any SATD marker different between academic and control repositories?) than for studies aimed at classifying SATD type. Alfayez et al.~\citep{alfayez2023tdtwitter} analyse 128,897 technical-debt-related posts on Twitter and find growing interest in the topic, grouped into 11 categories; we cite it as evidence that technical debt is widely discussed in practice, beyond the research literature.

For the SonarQube corroboration subsection, Amanatidis et al.~\citep{amanatidis2020td} build an empirical benchmark to evaluate how far different technical-debt measurement tools (including SonarQube) agree with each other, showing that the estimate obtained depends on the tool; this contextualises the discrepancy we observe between \texttt{jscpd} and SonarQube's duplication detectors as an instance of a documented pattern, not an anomaly specific to our sample or setup. Lenarduzzi et al.~\citep{lenarduzzi2019surgical} use data-driven regression models to estimate the additional project cost of sub-optimal code conditions and report that SonarQube's debt estimates can be made more precise; their work suggests both that automated TD estimation is an active research problem and that the tool's absolute figures are a starting point and not a ground truth, two assumptions that underpin our decision to use SonarQube as a corroboration instrument rather than as the primary measurement.


\section{Methodology}

\subsection{Sample construction}
Candidate academic repositories were identified via the GitHub search API using Spanish/Portuguese academic keywords (\emph{tesis}, \emph{trabajo de titulación}, \emph{proyecto integrador}, \emph{trabalho de conclusão}, \emph{tcc}, and related terms) combined with a language filter (Java, Python, JavaScript) and a minimum repository size of 200~KB (GitHub's size figure, which counts all files, not only source code), then verified by checking whether at least one of the repository's top contributors declares a Latin American city or country in their public GitHub profile location field. This combined keyword-plus-location approach is a heuristic, not a ground-truth label, and is discussed as a limitation below. Repositories with fewer than 10 commits were excluded. The GitHub search API excludes forked repositories by default unless a \texttt{fork:} qualifier is explicitly added, and none of our queries added one; we verified this by re-issuing representative academic- and control-sample queries and confirming \texttt{fork=false} for every returned repository, so the sample does not require a separate fork-filtering step. From 5{,}418 unique keyword-matched candidates, 300 were accepted as academic (274 successfully cloned and analyzed; the remainder had since been deleted, renamed, or were otherwise unreachable). A control sample of 300 non-academic repositories was drawn with one GitHub search per accepted academic repository: same language, repository size within $\pm 50\%$ of the academic repository's size, results ordered by last update (not by popularity, since an earlier version of this pipeline that sorted by star count pulled in large, well-known projects) and taken from a randomly chosen results page; repositories whose description contained one of the academic keywords were skipped (275 successfully analyzed). The control sample was not restricted to Latin American contributors and was not filtered by number of commits, so the two groups differ in more than their academic label: the comparison is between Latin American academic repositories and size- and language-matched GitHub repositories from any region (Limitations). Each control repository was drawn for one academic repository, but because clone failures broke many of those pairs, the analysis compares the two groups as independent samples, and we refer to the design as a matched-sample comparison, not a paired one.

Table~\ref{tab:country} reports the country and language composition of the 300 academic repositories, resolved from the GitHub profile location of each repository's top contributors (the same field used for the LatAm-verification heuristic above). Brazil accounts for nearly half the sample (47.7\%), consistent with Brazil's outsized share of Latin American GitHub activity; the remaining sample spans 15 further countries (16 in total).

\subsection{Metrics}
The primary metrics come from lightweight, license-compatible tools that jointly cover the target metric suite: \texttt{lizard} for cross-language cyclomatic complexity~\citep{mccabe1976complexity} and lines of code, \texttt{jscpd} for cross-language code duplication, and \texttt{ck} (a standard standalone reference tool that runs from a single \texttt{.jar} without requiring a SonarQube server) for the Chidamber and Kemerer~\citep{chidamber1994metrics} object-oriented metrics suite on the Java subset (coupling between objects, CBO; lack of cohesion, LCOM; depth of inheritance tree, DIT; weighted methods per class, WMC). Test coverage was not measured by executing test suites, which is infeasible across 600 arbitrary repositories without individualized build configuration; instead we report the proportion of source files that are test files by naming convention, an explicit proxy rather than measured coverage.

\subsection{SonarQube corroboration}
As a second instrument we ran SonarQube Community (standalone distribution, Java 21) on a fresh clone of the sample, since the clones used for the primary metrics had been deleted after extraction; 546 of the original 600 repositories could be re-cloned (274 academic, 272 control; a handful had since been deleted, renamed, or made private). SonarQube's Java analyzer refuses to run its full rule set on source files without matching compiled bytecode (\texttt{sonar.java.binaries}); since compiling 300-plus arbitrary student and hobby projects is infeasible without per-project build configuration, we pointed this property at an empty directory, which lets analysis proceed with Java-bytecode-dependent rules disabled while complexity, duplication, and code-smell detection remain intact. Under this configuration, 415 of the 546 re-cloned repositories (223 academic, 192 control) completed analysis successfully within a 150-second per-repository budget; the rest failed on very large repositories, unsupported content, or transient errors.

We treat this SonarQube-derived sample as a cross-tool consistency check on the \texttt{lizard}/\texttt{ck}-based findings above, not a replacement for them (it is smaller, and not repository-for-repository identical to the primary sample), comparing groups with the same Mann-Whitney/Holm/Cliff's-delta procedure on SonarQube-native metrics: cyclomatic and cognitive complexity per function, \texttt{duplicated\_lines\_density}, \texttt{sqale\_debt\_ratio} (SonarQube's own technical-debt-ratio metric, the specific metric our original substitution could not reproduce), and code smells per 1,000 lines.

\subsection{Statistical analysis}
Because software metrics are typically strongly right-skewed, we compare groups with the Mann-Whitney U test on each of nine metrics, apply the Holm correction for multiple comparisons, and report Cliff's delta~\citep{cliff1993dominance} as a non-parametric effect size, following standard practice for this kind of comparison in the empirical software engineering literature.

Three of the nine metrics remain significant after Holm correction (Figure~\ref{fig:boxplots}): the two cyclomatic-complexity measures and inheritance depth. All three concern complexity or design structure, but only inheritance depth moves in the hypothesized direction. Cyclomatic complexity is \emph{significantly lower} in academic repositories than in the control group, both on average (Cliff's $\delta=-0.37$, a medium effect) and at the maximum observed per repository ($\delta=-0.31$, small), contradicting our initial hypothesis that academic code would be more complex. Inheritance depth (DIT, Java subset only) is significantly higher in academic code ($\delta=+0.29$, small), consistent with the hypothesized pattern of less experienced object-oriented design. Coupling (CBO) trends in the hypothesized direction but does not survive correction ($p=0.350$). Duplication and test-file proportion show essentially no difference between groups ($\delta \approx 0.03$ and $-0.01$ respectively), and neither duplication nor size-driven variation in it separates the two groups (Figure~\ref{fig:nloc-dup}); notably, the median test-file proportion is \emph{zero in both groups} (Figure~\ref{fig:testfile}), meaning near-absent testing is not a distinguishing feature of academic code in this sample; it characterizes both groups about equally.

Because the control group is matched to the academic sample by language as well as by size, and cyclomatic complexity itself varies systematically by programming language, we checked whether the lower-complexity finding is an artifact of language composition. Table~\ref{tab:by-language} repeats the cyclomatic-complexity comparison separately within each of the three languages. The effect holds, and remains significant after a separate Holm correction across the three within-language tests, in all three: Java ($\delta=-0.41$), JavaScript ($\delta=-0.33$), and Python ($\delta=-0.49$), each with medium-to-large effect size. Language composition does not explain the aggregate result. Maximum complexity per repository grows with the number of functions, and the control repositories are somewhat larger (median 180 vs.\ 153 functions), so we also adjusted that comparison for size: in an OLS regression of $\log(\text{max CC})$ on group, the academic coefficient stays negative and significant with $\log(\text{NLOC})$ as a covariate ($\beta=-0.33$, $p<10^{-5}$) and with the log number of functions ($\beta=-0.40$, $p<10^{-7}$).

We also tested a second alternative explanation: that shorter-lived, less-maintained repositories, plausible for course projects that end when a semester does, explain the lower complexity instead of any academic/non-academic distinction. Using each repository's GitHub-reported creation and last-push dates (523 of 549 repositories resolved; the rest lacked a retrievable date), academic repositories are, if anything, longer-lived than control repositories (median 103.6 days versus 55.2 days, Mann-Whitney $p<0.001$), the opposite of what the maturity hypothesis predicts. An OLS regression of mean cyclomatic complexity on group membership and log-transformed repository lifespan leaves the group coefficient essentially unchanged from the unadjusted comparison ($-0.997$ unadjusted versus $-0.975$ adjusted, both $p<0.001$) while lifespan itself is not a significant predictor ($p=0.27$). Repository age does not explain the complexity difference.

SonarQube's own complexity metrics corroborate the \texttt{lizard}-based finding across tool architectures: academic repositories have significantly lower complexity per function, both cyclomatic (median 2.07 vs.\ 2.98, $\delta=-0.458$, medium effect, $p<10^{-14}$) and cognitive (median 1.31 vs.\ 3.00, $\delta=-0.426$, medium, $p<10^{-12}$), the same direction and a comparable effect size to the \texttt{lizard}-based result in Table~\ref{tab:results}. \texttt{sqale\_debt\_ratio}, SonarQube's own technical-debt-ratio metric that our original substitution could not reproduce, is significantly \emph{lower} in academic code ($\delta=-0.142$, $p=0.025$), consistent with, not contradicting, the lower-complexity result. Duplication tells a more mixed story: SonarQube's duplicate-code detector finds significantly \emph{higher} duplication in academic code (median 2.10\% vs.\ 0.80\%, $\delta=+0.181$, small effect, $p=0.003$), the opposite direction from \texttt{jscpd}'s null result in Table~\ref{tab:results} ($\delta\approx0.03$); the Discussion separates the roles of sample and detection threshold in this difference. Code smells per 1,000 lines do not differ between groups ($p=0.541$).

Figure~\ref{fig:efectos} shows the ten most frequent SonarQube code-smell types, normalized per 1,000 lines of code of each group. The most common smell in both groups is a JavaScript/React-specific rule (\emph{prop-types validation}, 3.4 and 3.3 per 1,000 lines), which reflects the language mix of the sample and not an academic-specific pattern. Academic code shows a higher rate of two style-convention smells (\texttt{let}/\texttt{const} usage, 1.25 vs.\ 0.18; package-naming convention, 1.14 vs.\ 0.08 per 1,000 lines), consistent with less mature tooling and linting setup and not with deeper structural problems. The default-unnamed-package smell (Java) goes the other way (0.11 academic vs.\ 2.38 control per 1,000 lines). These rates pool each group's lines of code, and we did not store counts by rule and repository, so we cannot tell whether a few repositories dominate a given rule; we therefore do not read the split as uniform across the ten smell types. Finally, we note that the SonarQube sub-sample suffers from differential attrition; see Limitations (\S6) for a full accounting of its impact.

\subsection{Self-admitted technical debt}

As a complement to the structural metrics above, we scanned source comments in the SonarQube sub-sample (223 academic and 191 control repositories with source available; one control repository's clone was missing) for self-admitted technical debt (SATD) markers (\texttt{TODO}, \texttt{FIXME}, \texttt{HACK}, \texttt{XXX}, \texttt{BUG}, and literal mentions of ``technical debt''), normalized per 1,000 lines of code. The median is zero in both groups (most repositories, academic and control alike, contain no SATD marker at all), but the distributions differ: a significantly larger share of academic repositories contain at least one SATD comment (42.2\% vs.\ 23.0\%), and academic repositories rank higher overall on this measure (Mann-Whitney $U=25{,}349.5$, $p<0.001$, Cliff's $\delta=+0.190$, small effect; IQR 0.00--0.52 academic vs.\ 0.00--0.00 control). This difference reflects typical repositories, not extremes: mean SATD density is actually higher in the control group (1.20 vs.\ 0.65 per 1,000 lines), because a handful of control repositories carry extreme outlier values (up to 120.9 per 1,000 lines) that Cliff's delta, an ordinal measure, is not sensitive to. Unlike the complexity result, this SATD finding runs \emph{with} the original hypothesis: academic developers more often leave explicit, self-admitted markers of incomplete or provisional work in their code than the control group does, even though the code that remains is structurally simpler by the metrics above.

\section{Discussion}

On this sample, academic Latin American repositories are structurally \emph{simpler}, not more complex, than the size-matched control group. One explanation we considered is a property of the control group, not of the academic group: because repositories were matched to the academic sample's typically modest size, the control sample necessarily excludes large, mature, well-known open-source projects and instead draws from the same broad population of small, low-visibility GitHub repositories that academic work is drawn from: personal projects, bootcamp exercises, and other non-professional code that is not actually representative of production software engineering practice. If the ``non-academic'' baseline is itself closer to informal, learning-stage code than to professionally maintained software, the comparison this paper runs is better described as \emph{labeled academic vs.\ unlabeled small repositories of unknown provenance} than as \emph{academic vs.\ professional}, which would materially change what a lower complexity score in the academic group means: it may reflect course-scoped assignments that are deliberately narrow in requirements, and not academic authors writing better-structured code than typical small non-academic projects. We could test this explanation only crudely. If the control group's low maturity drove the result, control repositories with signs of maturity should be more complex; using stars as that signal, they are less complex instead (median mean CC 2.16 for the 17 control repositories with at least five stars vs.\ 3.21 for the rest, $p=0.050$; Spearman $\rho=-0.14$ between stars and complexity, $p=0.026$). Stars are a weak maturity signal and few control repositories have them, so this does not refute the explanation, but it does not support it either, and the inverted complexity result remains unexplained. A curated control sample of engineered projects would be needed to settle it.

The DIT result, that academic code has measurably deeper inheritance hierarchies, is consistent with a specific, plausible mechanism: object-oriented design courses often assign or scaffold class-hierarchy exercises (e.g., requiring the use of inheritance to satisfy a rubric) in a way that unscaffolded personal projects do not, which would produce deeper hierarchies without those hierarchies reflecting either more sophisticated or more debt-laden design.

We take the near-zero test-file proportion in both groups, not only in the academic group, at face value: it suggests that the near-absence of testing culture in this size class of repository is a broader phenomenon than an academic-specific one, at least by this proxy metric, and that interventions aimed at improving testing practice in student software may be addressing a gap that is not actually specific to the classroom.

For software engineering teaching in the region, the results point to specific course-level habits, not to a general deficit in student code: inheritance used because an assignment requires it, almost no automated tests, and debt markers left in comments. Active-learning formats used in software engineering courses, among which a recent review in this journal finds games and project-based learning the most frequent, with team-based learning adopted in the authors' own department~\citep{irabedra2025active}, are natural places to make design review, a minimum of automated tests, and the clean-up of \texttt{TODO}/\texttt{FIXME} markers explicit deliverables. Because many of these habits carry over into industry, work on training software development teams in the region, which adapts teaching strategies to the learning style most common among practising developers~\citep{hidalgo2025crosscutting}, is a complementary route for the same practices after graduation.

That the SonarQube sub-sample reproduces the complexity result with a different parser makes it unlikely to be an artifact of \texttt{lizard}'s counting conventions, although both tools measure the same cyclomatic-complexity construct and the sub-sample is affected by differential attrition (Limitations), so this is a consistency check and not an independent replication. The lower \texttt{sqale\_debt\_ratio} in academic code is consistent with this: SonarQube's debt ratio aggregates many rule violations, beyond just complexity, so a lower ratio despite a higher duplication rate suggests that whatever is driving academic code's higher SonarQube-detected duplication is not enough, on its own, to outweigh the complexity advantage in SonarQube's own composite accounting.

The duplication discrepancy between \texttt{jscpd} on the primary sample (null) and SonarQube's detector on the 415-repository sub-sample (small, significant, academic higher) mixes two differences: the sample and the detection threshold. We separated them by running \texttt{jscpd} on the identical 415-repository sub-sample twice. With its default minimum block of 50 tokens it finds no significant difference (median 4.69\% vs.\ 3.16\%, Cliff's $\delta=+0.103$, $p=0.069$); with a stricter minimum of 100 tokens, which requires longer duplicated blocks, it finds higher duplication in academic code (median 1.77\% vs.\ 1.10\%, $\delta=+0.122$, $p=0.031$), the same direction as SonarQube. Holding the sample fixed, the threshold changes the significance of the result, while the sign of $\delta$ is positive at both settings. SonarQube's own copy-paste detector uses a different criterion for Java (at least 10 successive duplicated statements, whatever the number of tokens) and 100 tokens over at least 10 lines for the other languages, so no single \texttt{jscpd} setting reproduces it exactly; the remaining gap to SonarQube's effect size ($\delta=+0.181$) is consistent with that difference in how duplicated blocks are defined.

\section{Limitations}

The keyword-plus-contributor-location heuristic used to identify academic repositories is imperfect and can admit false positives (a repository containing the word ``tesis'' in an unrelated context) or miss true academic repositories that do not use any of the searched terms; we did not attempt manual verification at scale. The count of 5{,}418 keyword-matched candidates is the figure reported by our search script at collection time; the unfiltered candidate list was not archived, so that number cannot be re-derived from the released data, whereas the 300 accepted academic and 300 control repositories, and every metric computed on them, can. More generally, GitHub-mining studies are known to over-represent personal, inactive, and non-engineered projects unless explicitly filtered~\citep{kalliamvakou2014promises,munaiah2017curating}; our size threshold, minimum-commit filter, and (for the academic sample) contributor-location verification each narrow the sample somewhat in this direction, but we did not apply a dedicated engineered-project classifier, so some informal or abandoned repositories likely remain in both groups. The heuristic also identifies only GitHub repositories, excluding GitLab, institutional repositories, and any academic work never pushed to a public host at all, a substantial and likely non-random exclusion, since the most informal, least-polished student work is probably the least likely to be published publicly in the first place. As discussed above, the control group's size-matching means it should not be read as representative of professional software in general. The control group was also not restricted to Latin American contributors and was not filtered by number of commits, and its academic exclusion relied on repository descriptions only; regional origin, minimum activity, and academic status are therefore not held equal between the groups, and part of the differences may reflect them. Keyword-based SATD counts also depend on language and tooling conventions: some IDE templates insert \texttt{TODO} comments automatically, which would inflate counts in projects created from them. Test coverage is a naming-convention proxy, not measured execution coverage. \texttt{ck}'s object-oriented metrics apply only to the Java subset of each sample (roughly one third), reducing statistical power for CBO, LCOM, DIT, and WMC relative to the language-agnostic metrics. The SonarQube robustness check (Table~\ref{tab:sonarqube}) covers a smaller, non-identical sub-sample (415 of the original 546 re-cloned repositories) because source code had to be re-cloned from GitHub after the original clones were deleted to save disk space, and because SonarQube's Java analyzer, run without compiled bytecode, fails outright on some repositories instead of degrading gracefully. This attrition is not evenly distributed across groups: 223 of 274 academic repositories (81.4\%) completed analysis versus 192 of 272 control repositories (70.6\%), an 11-percentage-point gap, and failures skewed toward very large repositories, which are more common in the control group. We checked this by joining the primary sample's \texttt{lizard} complexity measurements to SonarQube-attrition status, attrited repositories are far larger than retained ones in both groups (median NLOC 5{,}497 vs.\ 1{,}229 academic, 7{,}709 vs.\ 1{,}369 control, $p<0.001$ both), which confirms size-driven analyzer failure as the mechanism. On complexity itself, attrited repositories trend higher than retained ones in the academic group (median \texttt{cc\_mean} 2.35 vs.\ 2.15) and lower in the control group (2.66 vs.\ 3.23), a pattern that, if it held up statistically, would mean the SonarQube sub-sample loses relatively complex academic repositories and relatively simple control repositories, which would widen the apparent academic-versus-control complexity gap in Table~\ref{tab:sonarqube} relative to the true populations, in the same direction as the paper's central finding. However, neither within-group difference reaches significance at these sample sizes ($p=0.34$ academic, $p=0.12$ control), so this remains an inconclusive pattern, and we do not treat the SonarQube corroboration as unbiased in its own right. Attrition here is counted against the primary sample (52 academic and 86 control repositories absent from the SonarQube results, the latter including the 3 that could not be re-cloned); the complexity comparison uses the 48 and 78 of them in which \texttt{lizard} found measurable functions. \texttt{sqale\_debt\_ratio} and the code-smell-type facets are SonarQube's default rule profile (``Sonar way''), not a profile tuned for either language mix or academic code specifically, and a different quality profile could shift the exact smell-type ranking in Figure~\ref{fig:efectos} without necessarily changing the aggregate complexity and debt-ratio results. Each control repository was drawn for one academic repository, but the pairs were not kept in the analysis (clone failures broke many of them); Mann-Whitney U, an independent-samples test, is therefore the test that matches the analysis we ran, and we refer to the design as matched-sample, not paired. The self-admitted technical debt (SATD) measure is a simple keyword count over source comments, not a validated SATD classifier; it covers only the 415-repository SonarQube sub-sample (not the full 549-repository primary sample, for the same disk-space reason discussed above), and it does not distinguish a genuine debt marker from an unrelated use of a common word (e.g.\ \texttt{BUG} inside an unrelated identifier or string), so the reported counts should be read as a coarse proxy, not a precise measurement. Lines of code is used both as a matching criterion (via the size band) and as one of the nine compared metrics (Table~\ref{tab:results}); its own comparison ($p=0.322$, not significant after correction) should be read as a check that the size-band matching worked as intended, not as an independent finding about repository size.
\section{Conclusion}

In a matched-sample comparison of 274 Latin American academic repositories against 275 size- and language-matched non-academic repositories, academic code shows significantly \emph{lower} cyclomatic complexity than the control group (the opposite of our initial hypothesis) while showing significantly deeper inheritance hierarchies, as hypothesized. Coupling, cohesion, duplication, and a test-coverage proxy show no significant difference after correction, and testing is near-absent in both groups, not distinctively academic. We do not have a confirmed explanation for the inverted complexity result: the composition of the size-matched control group, drawn from small, often informal repositories, is a plausible candidate, but a crude maturity check within the control group does not support it. We recommend that future comparative studies of academic code quality either use a professionally curated control set or explicitly frame their comparison as academic-versus-small-repository, not academic-versus-professional. A check with SonarQube Community on a 415-repository sub-sample reproduces the direction of the lower-complexity finding using SonarQube's own complexity metric and shows academic code has a lower SonarQube technical-debt ratio; because SonarQube and our primary tool compute the same underlying cyclomatic-complexity construct, we treat this as a cross-tool consistency check, not an independent replication, and the one clear point of disagreement across tools, duplication rate, depends on the detection threshold: on the same 415-repository sub-sample, \texttt{jscpd} finds no significant difference at its default threshold and higher duplication in academic code at a stricter one, the direction SonarQube reports, with a smaller effect size. On the same sub-sample, a self-admitted technical debt (SATD) comment count runs in the direction the original hypothesis expected, unlike the structural metrics: academic repositories more often contain explicit \texttt{TODO}/\texttt{FIXME}-style markers of unfinished work (Cliff's $\delta=+0.190$, $p<0.001$), even though the structural complexity of that code is lower.
